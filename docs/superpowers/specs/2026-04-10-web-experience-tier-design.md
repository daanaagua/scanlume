# Web 体验版与账户页修正设计

## 目标

在不破坏现有月付、年付与 API 购买链路的前提下，为 Scanlume 增加一个 `$1` 的一次性 Web 体验版，并同步修正账户页中仍然像“未开售”或“等待名单”的过渡期文案。

本轮设计希望同时解决两类问题：

- 让团队可以用真实金额跑一遍更接近线上状态的付款与 OCR 使用闭环。
- 让账户页的商业化状态与当前事实一致，不再误导用户认为支付尚未开放。

## 范围

- 新增一个一次性 Web 商品，价格为 `$1`，每个账号限购一次。
- 体验版额度按当前 `Starter $5 / 月 = 8000 credits` 折算为 `1600 credits`。
- 体验版购买成功后，额度可直接用于网页端 OCR 与 PDF OCR。
- 登录用户的 Web 余额解析与扣费顺序需要支持“订阅余额、体验版余额、免费余额”三层结构。
- ` /precos ` 增加体验版购买入口。
- ` /conta ` 去除等待名单与“尚未开售”类表述，并改为上线后的真实状态展示。
- 保持现有未登录购买意图、登录后继续结账、Creem 回跳到账户页的主路径不变。

## 不在本轮范围

- 不修改正式月付与年付套餐的价格、权益或订阅周期。
- 不把体验版做成可自动续费的特殊订阅。
- 不实现后台运营面板来手动管理体验版资格。
- 不在本轮实现优惠码驱动的体验版价格替代方案。
- 不自动在 Creem 中创建该产品；Creem 产品仍需人工创建并映射。

## 商品定义

### 体验版产品规则

- 内部产品 id 新增为 `web_experience_onetime`。
- 商品类型是一次性 Web credit 包，不是订阅。
- 售价固定为 `$1`。
- 发放 `1600 credits`。
- 默认有效期为 `30 天`，自支付成功时间开始计算。
- 每个账号只能购买一次。

### 展示与适用规则

- 未登录用户可以看到并点击体验版购买入口。
- 未登录点击后，沿用现有购买意图保存机制，登录或注册后回到账户页继续付款。
- 没有正式付费 Web 订阅、且未买过体验版的用户，显示可购买状态。
- 已买过体验版的用户，显示“已购买”或“已限购一次”，不再允许重复发起 checkout。
- 已有正式付费 Web 订阅的用户，不再将体验版作为主 CTA；可以弱化展示，或直接提示当前账号不适用体验版。

## 交互设计

### 定价页

- 在 `Web` 分类下新增一张独立的体验版卡片。
- 体验版卡片文案必须明确表达以下信息：
  - `$1`
  - 一次性
  - 限购一次
  - `1600 credits`
  - 适合先体验真实付款与 OCR 闭环
- 体验版不能伪装成 `Starter` 的月付优惠，避免与正式订阅混淆。
- 若账号已买过体验版，按钮显示“已购买”。
- 若账号已是正式付费 Web 订阅，按钮显示“当前账号不适用”或等价的禁用态提示。

### 账户页

- 删除等待名单与“未开售”过渡期信息，包括但不限于：
  - 等待名单卡片
  - `Versao paga de abril`
  - 暗示用户“未来才开放支付”的文案
- 保留并强化购买流卡片，但文案改为当前真实状态：
  - 支付已开放
  - 可继续购买正式套餐或体验版
  - 成功后可直接去 OCR 使用
- 购买体验版成功后，在账户页顶部显示明确完成态：
  - 体验版已到账
  - 当前可用 credits
  - 去 OCR 的 CTA
- 若体验版已购买且已用完或已过期，账户页应显示历史状态与不可重复购买说明，而不是重新开放购买。

## 后端模型设计

### 为什么不复用订阅表

当前登录用户的 Web 余额逻辑是：

- 若存在有效 Web 订阅，则优先读取订阅 bucket 作为余额。
- 若不存在订阅，则回落到免费账户余额。

如果把体验版硬塞进现有订阅模型，会带来以下问题：

- 一次性商品会被误表达为周期订阅。
- 后续取消、续费、周期结束语义会变得混乱。
- “限购一次”需要额外绕过订阅状态判断，逻辑会更脏。

因此本轮应新增一套轻量的一次性 Web credit 包模型。

### 新增数据结构

新增 `web_credit_packs`，用于保存一次性 Web credit 包。

建议字段：

- `id`
- `user_id`
- `product_id`
- `credits_total`
- `credits_remaining`
- `purchased_at`
- `expires_at`
- `status`

其中：

- `product_id` 用于标识 `web_experience_onetime`
- `status` 至少支持 `active`、`consumed`、`expired`

### 限购一次规则

限购一次必须由服务端保障，而不是只靠前端隐藏按钮。

服务端规则：

- 用户只要已有该产品的成功购买记录，或已有该产品对应的 `web_credit_pack`，就视为已用过体验版资格。
- 再次请求创建 `web_experience_onetime` checkout 时，直接拒绝，并返回明确错误码。

这样可以防止前端状态不同步或用户绕过页面按钮重复发起购买。

## 余额解析与扣费顺序

### 登录用户余额来源

登录用户的 Web 余额解析改为三层优先级：

1. 有效正式 Web 订阅
2. 有效体验版 credit 包
3. 免费账户余额

### 扣费顺序

实际 OCR 扣费顺序与余额展示顺序保持一致：

1. 先扣正式订阅余额
2. 若无正式订阅，则扣体验版余额
3. 若无体验版有效余额，则扣免费账户余额

### 正式订阅与体验版并存时的处理

- 若用户之后购买了正式订阅，正式订阅优先消费。
- 已存在的体验版 credit 包保留在库中，但不在正式订阅期间优先消费。
- 这样可以避免把正式套餐和体验版额度混成一个总池，降低用户理解成本。

## 购买与发放流程

### Checkout 创建

- ` /v1/billing/checkout ` 支持 `web_experience_onetime`。
- 若当前用户不符合购买资格，接口直接返回业务错误，不创建 Creem checkout。
- 若符合资格，则按现有 Creem checkout 创建路径发起请求。

### Creem 产品映射

- 运行时需要将 `web_experience_onetime` 加入 `CREEM_PRODUCT_MAP`。
- 在代码完成后，仍需手工在 Creem 中创建对应 `$1` 产品。
- 若映射缺失，后端应继续沿用当前错误风格，返回明确配置缺失错误。

### Webhook 发放

- 体验版成功支付后，不走订阅发放逻辑。
- webhook 应改为写入一次性 `web_credit_pack`。
- API 包、正式 Web 订阅保持现有逻辑不变。

## 账户快照与展示数据

账户快照需要增加对体验版状态的表达，至少满足以下需求：

- 当前是否已购买体验版
- 当前体验版是否仍有效
- 当前体验版剩余 credits
- 账户页是否还应展示体验版购买入口

账户页不需要展示复杂账单历史，但必须拿到足够信息来渲染：

- 可购买
- 已购买未用尽
- 已购买已用尽
- 已过期
- 当前账号已有正式订阅，不适用体验版

## 文案修正原则

本轮账户页文案要从“预热态”切换到“已开售态”。

文案原则：

- 不再暗示支付尚未上线。
- 不再保留等待名单作为主要商业化入口。
- 不把年度价目说明写成像内部审批备注的感觉。
- 对正式订阅与体验版的差异做清楚说明：
  - 体验版是一次性、限购一次、额度较小
  - 正式订阅适合持续使用

## 测试设计

### 后端测试

新增或扩展测试，覆盖：

- `web_experience_onetime` 可创建 checkout
- 不满足资格时无法重复创建体验版 checkout
- 体验版 webhook 可正确发放一次性 Web credits
- 登录用户余额解析遵循“订阅 > 体验版 > 免费”优先级
- 登录用户扣费逻辑遵循相同优先级

### 前端测试

新增或扩展测试，覆盖：

- 定价页渲染体验版卡片
- 已买过体验版时按钮不可再次购买
- 正式付费订阅用户不会看到误导性的体验版主购买态
- 账户页不再显示等待名单与“未开售”文案
- 体验版购买成功后显示正确的完成态与 CTA

### 手工验证

实现完成后需要至少手工验证以下路径：

1. 未登录用户从定价页点击体验版，登录后回到账户页继续付款
2. 体验版付款成功后，账户页显示到账状态
3. 用体验版 credits 实际跑一轮 OCR
4. 已买过体验版的账号再次尝试购买，被正确拦截
5. 正式订阅账号不会被体验版逻辑干扰

## 风险与兼容性

### 主要风险

- 登录用户 Web 余额当前主要围绕订阅实现，本轮会触碰余额读取与消费主路径，必须依赖测试保护。
- 若账户快照层未把体验版状态表达完整，前端容易出现“按钮可点但后端拒绝”的不一致体验。
- 若 Creem 产品未创建或未映射，体验版入口会在 checkout 创建阶段失败。

### 兼容性要求

- 现有 API 包购买链路不能受影响。
- 现有正式 Web 月付、年付购买和 webhook 发放逻辑不能受影响。
- 免费账户的既有 50 credits 行为不能受影响。

## 实施建议

推荐按以下顺序实现：

1. 先补后端模型与测试
2. 再接入 checkout 与 webhook
3. 然后改账户快照与扣费顺序
4. 最后改定价页与账户页文案

这样可以先把最容易出错的余额与限购逻辑稳定下来，再接用户界面。
